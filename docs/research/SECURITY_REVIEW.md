# Security, data-permission and release-readiness review

Reviewed 2026-11-24 by a separate Codex integration reviewer against the lead's then-uncommitted native application in `outputs/TechPulse`. This reviewer originally authored the provider module; its deadline hardening needs lead regression review rather than being described as an independent audit of that code. This is a focused source/probe review, not a penetration test, legal opinion, dependency-vulnerability certification or clean-machine release certification.

## Findings and disposition

| Finding | Initial evidence and impact | Remediation/recheck |

Userinfo-only URL validation did not uphold the credential-free source contract. | Lead added sensitive query/fragment rejection. Recheck rejected `api_key`, `x_cg_demo_api_key`, `X-Amz-Signature` and `client_secret`. This catches common parameter conventions, not arbitrary secrets hidden in document paths or prose. Users must still supply public, nonsensitive provenance. |

| P2: failed backup exception/handle lifecycle | Backing up to an existing non-SQLite file raised sqlite3.DatabaseError outside the original GUI catch; SQLite's connection context manager did not close the destination. | P2: stale/cross-workspace provider preview | A failed request retained prior `live_results` while the status claimed no stale result substituted; asynchronous completion could cross a workspace switch. | Lead clears results at request start/failure, forces research workspace and discards a response after a demo switch. | P2: request-count limits were not elapsed-time limits | Original HTTPX inactivity timeouts and page counts permitted a slow-drip response or many pages to keep the worker active far longer than one request timeout; the window refuses close while a worker is active. | Provider hardening adds one monotonic 60-second cooperative budget per public operation across pages/retries/rate waits and a maximum five-second network phase timeout. Five additional mocked-clock tests cover slow streams, shared page budget, refused late retry, shrinking timeout and expired rate wait. In-flight phase timeout can overrun the cooperative deadline by up to five seconds; no exact hard cancellation claim. |
| P3: rich-text interpretation of error messages | The static QMessageBox helper used default automatic text interpretation with parser-derived messages. | Lead changed errors to explicit PlainText. Record inspection already used setPlainText; standard labels also explicitly use PlainText. |

All initial findings were sent to the lead as soon as substantiated. Root changes were reviewed without editing its application/store/report files. Provider deadline changes were made in the provider worktree after explicit reassignment.

## Checks that passed

- HTML export probe with `<img ...><script>...</script>` in user-controlled report fields escaped the tags; no active script remained. Report data appears inside escaped preformatted text. PDF Paragraph inputs are HTML-escaped. Qt record inspection uses plain text.
- CSV section containing a leading `=HYPERLINK(...)` was prefixed with an apostrophe. JSON observation cells begin with JSON structural/quoted content; CSV writer handles delimiters and newlines.
- SQL operations parameterize values; there is no evaluated SQL, subprocess command or dynamic code path built from imported fields.
- A synthetic marker inserted only into `MainWindow.live_results` was absent from stored-data snapshots, local report archive payload, database and backup bytes. Network observations are session previews rather than persistent licensed datasets.
- Network endpoints are fixed official HTTPS URLs; redirects are disabled. Credentials use headers, not query URLs. Provider failures omit raw response bodies and request exception details. Original 34 provider tests passed during integrated review; after deadline hardening 39 provider tests passed in the worktree.
- `uv lock --check` succeeded against the integrated pyproject/lock. `pip check` reported no broken requirements. Lock sources were PyPI/pythonhosted URLs with hashes, not an unidentified private package registry.
- A targeted scan of source/tests/docs/workflows found no GitHub token, AWS access-key-ID or PEM private-key pattern. No secret values were printed. This is a limited pattern scan, not proof that arbitrary secrets cannot exist.
- Political automated collection remains disabled; no real political records are bundled. Fixed buttons open official sources. No paid service, brokerage execution route, hidden telemetry or network refresh on ordinary app startup was found in the inspected source.

## Remaining release gates and limitations

1. **Provider permission remains use-specific.** Session-only treatment minimizes retention; it does not automatically authorize every CoinGecko/Alpaca commercial use. No blanket legal clearance or redistribution rights are asserted. No actual restricted dataset should enter a GitHub release. Review `DATA_PROVIDERS.md` and applicable account terms.
2. **Local SQLite/imports/backups are unencrypted.** The import dialog states this and requires authorization covering local retention/export. No encrypted credential store is needed because keys are environment-only and not persisted. Do not import data requiring storage controls the application does not implement.
3. **Monthly/across-process API quotas are not managed.** Rate gates are process-local; no unattended network refresh exists. The 60-second budget is cooperative and a blocking phase may finish later by its configured timeout. No safe forced thread termination is attempted.
4. **Release assembly requires its own final check.** Verify MIT project license, Qt/LGPL and other dependency notices/source/relinking obligations, included files, exact lock and artifact hashes at the actual release commit. At review time packaging/notices were still being assembled; this document does not certify an installer or signed release.
5. **Broader security validation remains open.** No dependency advisory database scan, code signing, clean Windows machine test, long-running fuzz campaign or hostile filesystem-permission exercise was performed. `pip check` checks package compatibility, not vulnerabilities.
6. **Backup/report durability can improve.** Future releases should consider atomic file replacement, recovery UI for corrupt/locked databases, bounded backup progress/cancellation, and migration/restore testing. These are not grounds to claim current automated recovery beyond the specifically tested paths.

The preview is suitable for continued local research development after combined regression checks; a source/protocol review alone cannot certify production financial or legal correctness.
